## 5. Proposed data and transaction design

Use dedicated TypeORM/PostgreSQL commercial tables with UUID IDs, foreign keys, indexed queries, numeric quantities/amounts, optimistic version checks and transactional lifecycle commands. Keep NestJS/Next.js conventions and the existing database; a generic ERP framework rewrite is unnecessary.

| Record                              | Essential fields and constraints                                                                                                                                                                                                                |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Commercial enquiry extension        | Existing enquiry ID, organization, commercial status, exact quantity, customer site, requirements summary; preserve existing feasibility data and legacy quantity text                                                                          |
| Customer site                       | Customer and organization references, name/address/contact, active state; preserve immutable site snapshots on issued documents                                                                                                                 |
| Quote family / revision / line      | Stable family ID/number, revision sequence, predecessor/superseder, approval and customer-decision evidence, issue state, frozen party/site/commercial snapshots; line ID, item/UOM or explicit custom-scope line, exact quantities and amounts |
| Sales order / revision / line       | Source quote revision and line IDs, order number, PO reference/evidence, owner, order date, promised delivery, scope/terms, currency/net/tax/gross, approval record and lifecycle state; immutable confirmed revision                           |
| Commercial payment milestone        | Source revision, label, sequence, trigger or due date, agreed percentage/fixed amount, currency and amount basis; copied by reference-aware snapshot into order/project baseline                                                                |
| Project initiation baseline         | Existing project ID, source order revision, enquiry/quote lineage, project code, owner, machine categories/quantities, site, dates, agreed value and requirement/milestone snapshots; versioned baseline                                        |
| Approval / activity / evidence link | Record and exact revision, action, actor, timestamp, reason, customer evidence where applicable; attachment metadata/version and permission-aware source links                                                                                  |
| Idempotency / outbox                | Organization + operation + key uniqueness, request hash, result reference; durable events with deduplication and retry state                                                                                                                    |

Bridge existing JSONB domains deliberately: retain original enquiry/project IDs and introduce relational identity/source-link rows referencing the correct `runtime_documents` domain and ID, or normalize the touched domains completely. Package A must choose and test one approach. Do not declare a plain UUID column a foreign key to an unvalidated JSON property. Updates to an existing project document and its baseline must share the same transaction manager.

Proposed invariants:

1. One operative approved revision per quote family. Approving a replacement atomically supersedes the predecessor; a draft replacement does not erase the last approved history. A replacement requires its own customer acceptance before conversion.
2. Conversion rechecks current revision, acceptance, expiry rules, active references and actor permissions inside the transaction. An existing order retains its source revision even after a later quote amendment; changing the order needs its own approved amendment.
3. Subject to C05, a unique source-revision/order constraint and a unique order/project link enforce one conversion. A repeated request with the same key/payload returns the prior result; changed payload under that key fails. Concurrent requests cannot create duplicates.
4. Number allocation, new records, source links, history and durable events use a transaction-aware service. Unique document numbers remain protected by database constraints. Do not rewind issued sequences or silently reuse cancelled numbers.
5. Money uses decimal arithmetic and configured currency precision; quantities/UOM factors use separate precision. Persist net/tax/gross and tax basis snapshots. The server calculates totals; clients cannot override them. Milestones reconcile to the agreed configured amount basis with explicit rounding remainder handling.
6. Approval, issue, acceptance and conversion enforce active masters, customer/site ownership, organization scope, positive quantities, nonnegative allowed amounts, date ordering and an active permitted project owner. Drafts may be incomplete; submission/confirmation cannot be.
7. Organization identity is server-derived. Every list/detail/download/export and nested source lookup applies the same record-access policy. Approval authority and configurable separation of requester/approver are checked on the server.
8. Hold/cancel/amend actions require reason, actor/time and downstream-impact evaluation. Cancelling an order with an active project requires a controlled resolution; never cascade-delete commercial or engineering history. Accepted/approved/superseded records cannot be edited or reused through generic PATCH/DELETE endpoints.
9. Emit notifications only after commit using the durable event/outbox path. Approval, rejection/return, quote expiry and approaching milestone reminders are deduplicated and link to accessible source records.

## 9. New application schema and release handling

1. Use Release 1 organization, identity, permissions and masters as the foundation. Add R2 commercial tables, constraints, numbering and permissions through the versioned migration with `synchronize: false`.
2. Start new enquiries and quotations in Sales. Do not import or infer approvals for historical runtime documents. Existing unrelated workspace records are retained.
3. Generate the project baseline transactionally from its approved order. Existing direct enquiry/quote-to-project HTTP routes reject bypass attempts.
4. Verify migrations and the commercial workflow in an isolated test schema. No database reset or production backfill is part of R2 implementation.
5. Empty R2 tables can be reverted and reapplied; this is tested. Populated commercial tables refuse destructive migration reversal. Use a forward fix or a separately verified backup/restore procedure after business records exist.
